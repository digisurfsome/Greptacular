# PRD: CLI Build Orchestrator — AutoForge Workspace Integration

## What This Is

A dashboard inside the AutoForge workspace that lets users visually configure, orchestrate, and automate multi-agent builds using the Claude Code CLI system. Instead of manually writing agent files, commands, and hooks, users fill in forms, pick from dropdowns, and save reusable templates. The dashboard generates `.claude/` agent roles, commands, skills, and hooks — then automates the entire wave-based build process end to end.

**The difference from the SaaS web product (PRD 10):**
The SaaS product generates copy-paste prompts for users who work in browser-based AI chats (ChatGPT, Claude.ai, etc.). This CLI version generates `.claude/` configuration files that plug directly into the Claude Code CLI. The CLI version is more powerful because it can automate wave transitions, enforce quality gates via hooks, and spawn sub-agents — things the web-only version cannot do.

**The connection:** Both products share the same decomposition engine (breaking a PRD into agents, calculating token budgets, mapping dependencies into waves). The math differs slightly because CLI agents operate with different context constraints than browser chat sessions. But the core logic — dependency resolution, wave grouping, conflict detection — is identical and should be a shared service.

---

## Target User

Developers and power users who already have Claude Code CLI set up. They understand what agents, commands, and hooks are (or are willing to learn). They want the organizational power of multi-agent orchestration without manually writing dozens of markdown files and YAML configs.

**Not the target:** Complete beginners who have never used a terminal. Those users get the SaaS web product (PRD 10).

## How It Works (User Perspective)

### The Setup Flow

1. User opens the AutoForge workspace dashboard
2. Clicks "New Build Project" (or loads an existing one)
3. **Step 1 — Load PRD:** Pastes or uploads their PRD (or uses the PRD Maker to generate one). The decomposition engine analyzes it and auto-generates:
   - Feature list with size estimates
   - Dependency graph
   - Suggested wave breakdown
   - Token budget per agent
   - Suggested agent roles
4. **Step 2 — Configure Roles:** User reviews and customizes the agent roles. Each role is a card with:
   - Role name (Orchestrator, Architect, Builder, QA, Doc Writer, or custom)
   - Role prompt (pre-filled from the prompt library, editable)
   - Model selection (Opus, Sonnet, Haiku)
   - Assigned features (which features this role handles)
   - Rules/constraints (what files it can touch, what it cannot do)
5. **Step 3 — Configure Waves:** User reviews the auto-generated wave plan. Can:
   - Drag features between waves
   - Split or merge agents within a wave
   - Set quality gates between waves (lint, build, test, manual review)
   - Set hook triggers (what happens when a wave completes)
6. **Step 4 — Configure Hooks:** User sets up automation hooks:
   - Pre-wave hooks (setup, environment checks)
   - Post-wave hooks (lint, build, test, merge verification)
   - Wave transition hooks (auto-start next wave when current passes gates)
   - Failure hooks (what to do when a gate fails — retry, alert, stop)
7. **Step 5 — Save as Template:** User saves the entire configuration (roles, waves, hooks, prompts) as a named template. Can load it for future projects with one click.
8. **Execute:** User clicks "Start Build" and the system:
   - Generates all `.claude/` files (agents, commands, hooks)
   - Starts Wave 1 agents in parallel
   - Monitors progress via WebSocket
   - Runs quality gates when Wave 1 completes
   - Auto-transitions to Wave 2 (if gates pass)
   - Continues through all waves
   - Runs final QA wave
   - Reports results on the dashboard

### The Runtime View

While a build is running, the dashboard shows:
- **Wave progress bar** — which wave is active, which are done, which are pending
- **Agent cards** — one per active agent, showing: role, assigned features, status (thinking/building/testing/done/error), live log output
- **Quality gate status** — pass/fail for each gate between waves
- **Dependency graph** — visual graph with nodes colored by status (pending/active/done/failed)
- **Build timeline** — horizontal timeline showing wave transitions, gate checks, and agent activity

## Core Features

### Feature 1: PRD Decomposition Engine

**What it does:** Takes a PRD (structured or unstructured text) and breaks it down into buildable units with dependency relationships, token estimates, and wave assignments.

**This is the shared engine with PRD 10.** Same core logic, different output format. The SaaS version outputs copy-paste prompts. The CLI version outputs `.claude/` configuration files.

**Engine inputs:**
- PRD text (pasted, uploaded, or generated by PRD Maker)
- Target model and context window size
- Number of available parallel agent slots (from AutoForge settings)

**Engine outputs:**
- Feature list with: name, description, size (small/medium/large), estimated tokens
- Dependency graph: which features depend on which
- Wave plan: features grouped into sequential waves, with parallel agents within each wave
- Token budget table: per-agent token usage vs available context
- File ownership map: which files each agent will create or modify
- Conflict risk matrix: files touched by multiple agents in the same wave

**CLI-specific adjustments (vs SaaS version):**
- CLI agents have access to the full filesystem, so context injection is different (agents read files directly instead of having docs pasted in)
- CLAUDE.md serves as the shared context document (no need to paste Vision/Context Primer into every prompt)
- Token budgets account for CLAUDE.md overhead, MCP server overhead, and hook execution overhead
- Agents can be smaller and more focused because they read files on demand instead of front-loading everything into the prompt

**AI integration:**
- Uses Claude API to analyze PRD text and generate feature breakdowns
- Dependency detection is AI-assisted (analyzes feature descriptions to infer which features depend on which)
- Wave grouping uses algorithmic optimization (Kahn's algorithm for topological sort, same as existing `dependency_resolver.py`)

### Feature 2: Role Configuration Dashboard

**What it does:** Visual interface for defining and customizing agent roles. Each role becomes a `.claude/agents/*.md` file.

**Pre-built roles (ship with the product):**

| Role | File | Purpose | Model |
|------|------|---------|-------|
| Orchestrator | `orchestrator.md` | Manages the build, spawns sub-agents, does not write code | Opus |
| Architect | `architect.md` | Designs interfaces, file structure, data models. Output only, no implementation | Opus |
| Builder | `builder.md` | Implements features following the architect's blueprint exactly | Sonnet |
| QA | `qa.md` | Tests features, breaks things, reports bugs with reproduction steps | Sonnet |
| Reviewer | `reviewer.md` | Code review, security audit, performance analysis | Opus |
| Doc Writer | `doc-writer.md` | Reads the code, writes user-facing documentation | Sonnet |
| Fixer | `fixer.md` | Takes QA reports, fixes bugs, re-runs tests | Sonnet |
| Integrator | `integrator.md` | Merges wave outputs, resolves conflicts, verifies combined build | Opus |

**Role card UI fields:**
- **Name** — display name and filename
- **Role prompt** — the markdown content that defines personality, focus, and constraints (editable text area with markdown preview)
- **Model** — dropdown: Opus, Sonnet, Haiku
- **Scope** — which files/directories this role can touch (whitelist)
- **Restrictions** — what this role cannot do (e.g., "do not modify database schema", "do not install dependencies")
- **Quality gates** — what checks this role must pass before its work is accepted (lint, build, test, custom command)
- **Prompt source** — "Custom" or select from Prompt Library

**Role editing features:**
- Edit role prompt inline with markdown preview
- "Load from Library" button — pulls a role prompt from the prompt library
- "Save to Library" button — saves current role prompt to the library
- Duplicate role (create a variant)
- Import/export role as `.md` file

**Generated output:**
Each role becomes a `.claude/agents/{name}.md` file with YAML frontmatter:

```yaml
---
name: Builder
model: sonnet
description: Implements features following architect blueprints
---

# Builder Agent

You are a builder agent. Your job is to implement features...
[role prompt content]
```

### Feature 3: Wave Orchestration Dashboard

**What it does:** Visual interface for organizing features into waves, setting parallel agent groups, defining quality gates, and automating wave transitions.

**Wave view UI:**
- Horizontal lanes, one per wave (Wave 1, Wave 2, ..., QA Wave)
- Feature cards within each lane (draggable between lanes)
- Parallel groups within a lane (features in the same group run simultaneously)
- Dependency arrows between features across waves
- Quality gate indicators between waves (green checkmark / red X / gray pending)

**Wave configuration per wave:**
- **Agent assignments** — which roles handle which features in this wave
- **Parallelism** — how many agents run simultaneously (1-5, from AutoForge settings)
- **Quality gates** — checks that must pass before the next wave starts:
  - Lint (ruff, eslint)
  - Build (type check, compile)
  - Test (unit tests, integration tests)
  - Manual review (pause for human approval)
  - Custom command (any shell command)
- **Transition behavior** — what happens when gates pass:
  - Auto-start next wave (fully automated)
  - Notify and wait (sends notification, waits for user to click "Continue")
  - Run integrator first (spawn integrator agent to merge and verify before next wave)
- **Failure behavior** — what happens when a gate fails:
  - Spawn fixer agent (auto-fix and re-run gates)
  - Retry wave (re-run the failing agents)
  - Stop and alert (halt the build, notify user)
  - Rollback (git reset to pre-wave state, requires confirmation)

**Hook generation:**
The wave configuration generates `.claude/hooks/` files and updates the AutoForge hook system:

```yaml
# .autoforge/hooks/wave-transition.yaml
hooks:
  post_wave_1:
    quality_gates:
      - command: "ruff check ."
        name: "Lint"
        required: true
      - command: "npm run build"
        name: "Build"
        required: true
    on_pass: "auto_start_wave_2"
    on_fail: "spawn_fixer"

  post_wave_2:
    quality_gates:
      - command: "npm run build"
        name: "Build"
        required: true
      - command: "python -m pytest"
        name: "Tests"
        required: true
    on_pass: "auto_start_qa_wave"
    on_fail: "stop_and_alert"
```

**Generated command files:**
The orchestration plan generates `.claude/commands/` files:

```markdown
# .claude/commands/build-feature.md
---
description: "Build a single feature: architect → builder → qa"
---

Chain the following agents in sequence:
1. Run architect agent to design the feature structure
2. Run builder agent to implement the design
3. Run qa agent to verify the implementation
```

```markdown
# .claude/commands/full-build.md
---
description: "Execute the complete multi-wave build plan"
---

Execute all waves in sequence with quality gates between each:
1. Wave 1: [features] — parallel agents
2. Quality gate: lint + build
3. Wave 2: [features] — parallel agents
4. Quality gate: lint + build + test
5. QA Wave: full verification
```

### Feature 4: Prompt Library

**What it does:** A central library for storing, organizing, tagging, and reusing prompts across projects. One library for everything — role prompts, hook prompts, system prompts, custom instructions — organized by tags.

**This is a single unified library, not separate libraries per category.** Tags handle organization.

**Library item fields:**
- **Name** — display name
- **Content** — the prompt text (markdown)
- **Tags** — one or more tags from a managed tag list
- **Description** — one-line summary of what this prompt does
- **Created/Updated** — timestamps
- **Usage count** — how many projects reference this prompt
- **Source** — "Built-in", "User", or "Imported"

**Pre-built tag categories:**

| Tag | What It Covers |
|-----|---------------|
| `role:orchestrator` | Orchestrator role prompts |
| `role:architect` | Architect role prompts |
| `role:builder` | Builder role prompts |
| `role:qa` | QA/testing role prompts |
| `role:reviewer` | Code review role prompts |
| `role:doc-writer` | Documentation role prompts |
| `role:fixer` | Bug-fixing role prompts |
| `role:integrator` | Merge/integration role prompts |
| `hook:pre-build` | Pre-build hook prompts |
| `hook:post-build` | Post-build hook prompts |
| `hook:quality-gate` | Quality gate definitions |
| `hook:transition` | Wave transition logic |
| `pattern:clean-room` | Clean room methodology prompts |
| `pattern:tdd` | Test-driven development prompts |
| `pattern:security-first` | Security-focused constraints |
| `stack:react` | React-specific instructions |
| `stack:python` | Python-specific instructions |
| `stack:node` | Node.js-specific instructions |
| `feature:auth` | Authentication feature prompts |
| `feature:crud` | CRUD feature prompts |
| `feature:dashboard` | Dashboard feature prompts |

**Users can create custom tags.** Tags are freeform strings with a `category:value` convention.

**Library UI:**
- **List view** — all prompts, sortable by name, date, usage count
- **Filter by tags** — multi-select tag filter, narrows the list
- **Search** — full-text search across name, description, and content
- **Preview panel** — click a prompt to see its full content on the right
- **Actions** — Edit, Duplicate, Delete, Export, "Use in Project"

**Library integration points:**
- Role Configuration Dashboard: "Load from Library" button on each role card
- Wave Configuration: "Load hook prompt from Library" for quality gate definitions
- Template system: templates reference library items by ID (so updating a library prompt updates all templates that use it)

**Import/Export:**
- Export individual prompts as `.md` files
- Export filtered set as a `.zip`
- Import `.md` files into the library
- Import from shared team library (future: shared prompt packs)

### Feature 5: Template System

**What it does:** Save an entire project configuration (roles, waves, hooks, prompts, quality gates) as a named template. Load a template to instantly set up a new project with pre-configured everything.

**What a template contains:**
- Project metadata (name pattern, description, tech stack)
- Role configurations (which roles, with which prompts, which models)
- Wave plan (how many waves, what goes in each, parallel groups)
- Quality gate configurations (which gates between which waves)
- Hook configurations (pre/post wave, transition, failure behavior)
- Prompt library references (which library prompts are used where)

**Pre-built templates (ship with the product):**

| Template | Use Case | Roles | Waves |
|----------|----------|-------|-------|
| **Quick Build** | Small apps (3-5 features), fast iteration | Builder + QA | 2 waves |
| **Standard Build** | Medium apps (5-10 features), balanced quality | Architect + Builder + QA | 3 waves |
| **Enterprise Build** | Large apps (10+ features), maximum quality | All 8 roles | 4+ waves |
| **Clean Room** | Rebuild from spec, no reference to old code | Architect + Builder + Reviewer + QA | 3 waves with strict gates |
| **TDD Build** | Test-first development | Architect + QA (write tests) + Builder (make tests pass) | 3 waves, tests before code |
| **Security Audit** | Security-focused build with audit gates | Builder + Reviewer (security) + QA | 3 waves with security gates |
| **Rapid Prototype** | YOLO-style fast build, minimal gates | Builder only | 1 wave, lint-only gate |

**Template UI:**
- **Template browser** — grid of template cards with name, description, role count, wave count
- **Template detail** — click to see full configuration preview
- **"Use Template"** — creates a new project pre-filled with the template configuration
- **"Save as Template"** — saves current project configuration as a new template
- **"Edit Template"** — modify an existing template
- **Import/Export** — share templates as JSON files

**Template storage:**
- Stored in the AutoForge database (SQLite, consistent with existing patterns)
- Each template is a serialized JSON blob of the full configuration
- Template references prompt library items by ID (not by content copy — so library updates propagate)

### Feature 6: Build Execution Engine

**What it does:** Takes the configured wave plan and executes it end to end, automating agent spawning, quality gates, wave transitions, and progress tracking.

**This extends the existing `parallel_orchestrator.py` and `process_manager.py`.** It does not replace them — it adds wave-level orchestration on top.

**Execution flow:**

```
User clicks "Start Build"
    │
    ├── Generate .claude/ files from dashboard configuration
    │   ├── .claude/agents/*.md (one per role)
    │   ├── .claude/commands/full-build.md
    │   └── .autoforge/hooks/wave-transition.yaml
    │
    ├── Wave 1
    │   ├── Spawn parallel agents (using existing parallel_orchestrator)
    │   ├── Monitor agent progress (WebSocket updates to dashboard)
    │   ├── Wait for all Wave 1 agents to complete
    │   └── Run quality gates
    │       ├── PASS → proceed to merge
    │       └── FAIL → execute failure behavior (retry / fix / stop)
    │
    ├── Merge Point
    │   ├── If integrator role is configured: spawn integrator agent
    │   ├── Verify combined build compiles
    │   └── Git commit checkpoint
    │
    ├── Wave 2
    │   ├── (same as Wave 1 but with Wave 2 features)
    │   └── ...
    │
    ├── Wave N...
    │
    └── QA Wave
        ├── Spawn QA agents (verification, not building)
        ├── Collect QA reports
        ├── If issues found: spawn fixer agents
        ├── Re-run QA on fixes
        └── Final report to dashboard
```

**WebSocket events (extends existing pattern):**

| Event | Data | When |
|-------|------|------|
| `wave_start` | `{ wave: number, agents: [...], features: [...] }` | Wave begins |
| `wave_progress` | `{ wave: number, agent: string, status: string }` | Agent status change |
| `gate_start` | `{ wave: number, gate: string }` | Quality gate running |
| `gate_result` | `{ wave: number, gate: string, passed: boolean, output: string }` | Gate completes |
| `wave_complete` | `{ wave: number, passed: boolean }` | All agents + gates done |
| `merge_start` | `{ wave: number }` | Merge/integration phase begins |
| `merge_complete` | `{ wave: number, conflicts: [...] }` | Merge done |
| `build_complete` | `{ waves: number, features: number, duration: string }` | Entire build done |

**Progress persistence:**
- Build state saved to database so dashboard can reconnect after browser refresh
- Each wave/agent/gate status persisted
- Git checkpoint commits at each merge point (using existing checkpoint command pattern)

### Feature 7: Project Management

**What it does:** Save, load, and manage build projects. Each project stores its PRD, configuration, build history, and generated files.

**Project data model:**
- Project name and description
- PRD content (the source document)
- Decomposition output (features, dependencies, waves)
- Role configurations (which roles with which prompts)
- Wave plan (the orchestration configuration)
- Hook configurations
- Template reference (which template it was created from, if any)
- Build history (past executions with timestamps, durations, results)
- Generated files (the `.claude/` output)

**Project list view:**
- Card grid showing all projects
- Status badge: Draft (configuring), Ready (configured, not yet built), Building (in progress), Complete, Failed
- Last built date
- Feature count and completion percentage
- Quick actions: Open, Duplicate, Delete, Export

**Project detail view:**
- Tabs: PRD | Configuration | Build History | Generated Files
- **PRD tab** — the source PRD with decomposition results
- **Configuration tab** — roles, waves, hooks, gates (the full dashboard)
- **Build History tab** — list of past executions with expandable details (agent logs, gate results, duration)
- **Generated Files tab** — preview of all `.claude/` files that will be / were generated

### Integration with Existing AutoForge Systems

**Parallel Orchestrator (`parallel_orchestrator.py`):**
The build execution engine calls into the existing parallel orchestrator for spawning agents within a wave. The new layer adds wave sequencing, quality gates, and transition logic on top.

**Process Manager (`process_manager.py`):**
Agent lifecycle (start, stop, pause, resume) uses the existing process manager. The build orchestrator tracks which processes belong to which wave.

**Feature MCP Server (`mcp_server/feature_mcp.py`):**
Each build project can optionally create a feature database that the MCP server manages. This lets agents use `feature_mark_passing` etc. during the build.

**WebSocket (`websocket.py`):**
New event types are added alongside existing ones. The build orchestrator broadcasts wave/gate/merge events through the same WebSocket infrastructure.

**Dependency Resolver (`api/dependency_resolver.py`):**
The decomposition engine uses the existing Kahn's algorithm implementation for topological sorting of features into waves.

## Shared Engine Architecture

The decomposition engine is shared between PRD 10 (SaaS) and PRD 11 (CLI). It should be implemented as an isolated service that both products call.

**Shared service interface:**

```python
class DecompositionEngine:
    """Breaks a PRD into buildable units with dependency relationships."""

    def decompose(
        self,
        prd_text: str,
        context_window: int = 200_000,
        max_parallel_agents: int = 3,
        mode: Literal["web", "cli"] = "cli"
    ) -> DecompositionResult:
        """
        Returns:
          - features: list of Feature(name, description, size, estimated_tokens)
          - dependencies: list of (feature_id, depends_on_feature_id)
          - waves: list of Wave(number, features, parallel_groups)
          - token_budgets: dict of feature_id -> TokenBudget(used, available, percentage)
          - file_map: dict of feature_id -> list of FileAction(path, action=create|modify)
          - conflicts: list of ConflictRisk(file, agents, severity)
        """
```

**Mode differences:**
- `web` mode: Calculates token budgets assuming foundation docs are pasted into each prompt. Generates monolithic prompts.
- `cli` mode: Calculates token budgets assuming CLAUDE.md provides shared context and agents read files directly. Generates focused role files. Accounts for MCP server overhead and hook execution overhead.

## What This Does NOT Do

- **Does not replace the existing AutoForge agent system.** The existing Initializer + Coding Agent flow stays as-is. This is a separate, more structured orchestration layer for users who want wave-based builds.
- **Does not require any changes to Claude Code CLI itself.** It generates standard `.claude/` files that the CLI already understands.
- **Does not make API calls to AI during builds.** The agents themselves are Claude Code CLI sessions. The only AI API calls are during PRD decomposition (analyzing the PRD to generate features).
- **Does not handle billing or subscriptions.** This is a feature inside AutoForge, not a separate paid product. Users who have AutoForge have this.
