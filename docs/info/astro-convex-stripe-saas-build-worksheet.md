# SaaS Launch Boilerplate: Astro + Convex + Stripe
**Source:** Income Stream Surfers video — Opus 4.7 live build demo  
**Purpose:** Agnostic agency boilerplate — swap the middle for anything you're selling

---

## The Core Idea

This is a 3-layer stack. The top and bottom never change. Only the middle swaps.

```
┌─────────────────────────────────────────┐
│  TOP LAYER  — Astro (frontend/UI)       │  ← always the same
├─────────────────────────────────────────┤
│  MIDDLE LAYER — what you're selling     │  ← swappable
├─────────────────────────────────────────┤
│  BOTTOM LAYER — Convex + Stripe         │  ← always the same
└─────────────────────────────────────────┘
```

The boilerplate = top + bottom. The Archon skill = determining what goes in the middle and wiring it up.

---

## Full Tech Stack (Boilerplate Core)

| Layer | Tool | Notes |
|-------|------|-------|
| Frontend | **Astro** | SSR mode, dictionary-based i18n from day one |
| Database / Backend | **Convex** | DB + functions + backend as a service. Stores products, orders, most secrets |
| Payments | **Stripe** | Dynamic pricing — price sent from Convex to Stripe. No Stripe product catalog needed |
| Email | **Resend** | Order/purchase confirmation emails |
| Auth / Accounts | **Clerk** | Customer accounts, order history (optional layer) |
| Deployment | **Vercel** | CLI-based push. Convex handles most env vars so minimal Vercel config |
| Repo | **GitHub** | CLI-based creation and push |
| AI Coding Agent | **Claude Desktop App (Claude Code)** | Opus 4.7, medium thinking |

## What Can Go in the Middle

The middle is whatever you're actually selling. The boilerplate doesn't care. Examples:

**Physical / Print**
- Print-on-demand products (posters, canvas, apparel via Gelato/Printify)
- Custom merchandise tied to a brand or creator
- Limited edition drops

**Digital Products**
- PDF guides, templates, swipe files
- Notion dashboards or Figma kits (download on purchase)
- Prompt packs, SOPs, playbooks

**SaaS / Software**
- Landing + checkout page for a SaaS (Stripe handles subscription billing)
- Lifetime deal page (LTD launch)
- Waitlist + early access funnel with Stripe hold/charge

**Services**
- Coaching / consulting booking (Stripe deposit or full pay)
- Done-for-you agency service checkout
- Fractional work or retainer signup

**AI-Generated Products**
- Any product where the "thing" is generated by AI at purchase time
- Custom portraits, personalized content, generated assets
- The AI layer sits in the middle — Open Router or direct API call

**Content / Community**
- Course or membership access (Stripe → Clerk gate)
- Newsletter paid tier
- Private community access

**Lead Gen / Funnel**
- Free + paid lead magnet with upsell
- Quiz funnel with product recommendation + Stripe at the end
- Multi-step application form with deposit

## Step-by-Step Build Workflow (Agnostic)

### Phase 1 — Project Scaffolding (Minutes 0–4)

**Step 1: Open Claude Desktop, new workspace**
- Opus 4.7
- Optional: say "do not use any skills here" if you want raw build without shortcuts

**Step 2: Init Astro + Convex**

Prompt:
```
help me set up Astro with convex to start please. I can run commands if needed. For example, convex is interactive terminal.
```

**Step 3: Run Convex in terminal**
```bash
npx convex dev
```
- Name the project (your brand/project name)
- Creates: database, functions, backend — everything
- Astro sits on top

**Step 4: Verify project runs** (Claude usually does this automatically)

---

### Phase 2 — Stripe Setup (Minutes 4–6)

**Step 5: Request dynamic Stripe setup**

Prompt:
```
please set up Stripe whereby you can store a price in convex and when someone goes to buy said object it charges them the price given to it instead of me making Stripe products. Also give me the Stripe webhook to set up in my Stripe dashboard.
```

**Step 6: Get Stripe test keys**
- Stripe Dashboard → Developers → API Keys
- Copy: `pk_test_...` and `sk_test_...`

**Step 7: Feed keys to Claude**

Prompt:
```
these are my stripe variables: [paste keys]
Please add — make sure that everything is easily changeable so I can just switch to live Stripe variables later and we're live. Thanks.
```

**Step 8: Create Stripe webhook**
- Stripe Dashboard → Developers → Webhooks → Add endpoint
- URL: whatever Claude gives you
- Events: `checkout.session.completed` + anything else Claude specifies
- Copy `whsec_...`

**Step 9: Store webhook secret**

Prompt:
```
please also store my whsec: [paste secret]. Put it in the env variables.
```

---

### Phase 3 — First Test Buy (Minute 6)

**Step 10: Seed a test product and verify end-to-end**
- Claude seeds a dummy product
- Click Buy → use test card `4242 4242 4242 4242`, any future date, any CVC
- Verify: webhook fires, order shows as `paid`

**Checkpoint:** Full payment loop working ~6 minutes from zero.

---

### Phase 4 — Wire the Middle (Variable Time)

This is the only phase that changes per project. You're describing what gets delivered when someone pays.

**Prompt pattern:**
```
[describe what happens when someone buys]
Connect [your fulfillment/delivery mechanism] using [API/tool].
Test it locally as a script first before wiring to the frontend.
```

**Examples of what "the middle" looks like per product type:**

| What You're Selling | The Middle |
|---------------------|-----------|
| Print on demand | Gelato/Printify API — draft order on purchase |
| Digital download | Convex file storage — generate signed URL on purchase |
| SaaS access | Clerk — grant role/tier on webhook |
| Course access | Clerk + gated route — unlock on payment |
| AI-generated product | Open Router call — generate asset at purchase time |
| Coaching booking | Calendly/Cal.com embed — send booking link on purchase |
| Service retainer | Trigger onboarding email sequence via Resend |

**Critical pattern — always test the middle as a local script first:**

Prompt:
```
build this as a standalone test script first. I want to confirm the [delivery mechanism] works end-to-end before we wire it to the UI.
```

Get the script passing. Then wire to frontend.

---

### Phase 5 — Full Site Build (Minutes ~20–35 depending on complexity)

**Step 11: One-shot full site prompt**

Template:
```
create the entire website for [BUSINESS NAME]. 

What we're selling: [describe the product/service in plain language]
The offer: [price, what they get, any variants]
Design direction: [minimal/bold/luxury/fun — wow me with the design]
Use dictionaries throughout — English first, we'll add languages later.

User flow: [landing/hero] → [product/offer page] → [checkout] → [confirmation/access page]

Do it.
```

**Non-negotiable prompt elements:**
- "Use dictionaries throughout" — mandatory for i18n. Skip this and you refactor everything later.
- Describe the full user flow in one line
- Give design direction so it has creative latitude

---

### Phase 6 — i18n / Translation (Optional, ~5 min per language)

Prompt:
```
translate this entire site into [LANGUAGE] and put it at /[LANG_CODE]
```

If you forgot dictionaries on Phase 5, first run:
```
make this fully language-aware using dictionaries, then translate to [LANGUAGE] at /[LANG_CODE]
```

---

### Phase 7 — Deploy (Minutes ~40–45)

**Pre-requisite (terminal, before prompting):**
```bash
vercel login
gh auth login
```

**Step 12: Create repo and deploy**

Prompt:
```
create a GitHub repo and then push this to Vercel. You have the Vercel CLI.
```

Claude: creates repo → pushes → deploys via `vercel --prod`.

**Why almost no Vercel env vars:** Convex holds most secrets. Minimal Vercel config needed.

**Step 13: Go live**
- Add domain in Vercel dashboard
- Swap Stripe test keys → production keys
- Done.

## Key Patterns (Apply to Every Build)

### Stripe Dynamic Pricing
Never create Stripe products. Store price in Convex, send it dynamically at checkout:
```
{ amount: price_from_db, currency: 'usd' }
```
One Stripe account. Unlimited SKUs. No product catalog management.

### Local-Script-First
Always build the "middle" as a standalone script before touching the UI:
1. Build script → test script → fix → perfect
2. Then plug into Astro
3. Never debug the middle through the UI — too slow

### Dictionary-First i18n
Say "use dictionaries throughout" in every site-build prompt. Costs nothing upfront. Saves a full refactor when you add language routes later.

### Convex as the Hub
Convex holds products, prices, orders, generated assets, and most API keys. This is why Vercel config is nearly empty at deploy time.

## Archon Workflow Map

### The Fixed Boilerplate Workflow (runs every time)

```
[Node 1] Project Init
  Input: project name
  Steps: scaffold Astro + Convex, run npx convex dev
  Output: working dev server

[Node 2] Stripe Core
  Input: Stripe test keys
  Steps: dynamic pricing setup, webhook endpoint, store whsec
  Output: working test checkout

[Node 3] Test Buy
  Input: none
  Steps: seed product, test card purchase, verify webhook
  Output: confirmed payment loop

[Node 4] → MIDDLE SKILL SLOT ←
  Input: output from Middle Selector skill
  Steps: whatever the middle requires
  Output: delivery mechanism tested end-to-end

[Node 5] Full Site Build
  Input: brand name, offer description, design direction, user flow
  Steps: one-shot site build with dictionaries
  Output: complete Astro site

[Node 6] i18n (optional)
  Input: target languages
  Steps: translate + add routes
  Output: multi-language site

[Node 7] Deploy
  Input: GitHub + Vercel credentials
  Steps: create repo, push, vercel --prod
  Output: live URL

[Node 8] Go Live
  Input: production Stripe keys, custom domain
  Steps: swap vars, add domain
  Output: live business
```

### The Middle Selector Skill (separate Archon skill)

This skill takes what you're selling and outputs the Node 4 configuration:

```
Input: what are you selling?

→ Print on demand physical product
   → Use: Gelato or Printify API
   → Node 4 builds: product webhook, draft order on payment

→ Digital download
   → Use: Convex file storage
   → Node 4 builds: signed URL generation on payment

→ SaaS / software access
   → Use: Clerk roles
   → Node 4 builds: role grant on webhook, gated routes

→ Course / membership
   → Use: Clerk + gated Astro routes
   → Node 4 builds: access unlock on payment

→ AI-generated product
   → Use: Open Router (model TBD per use case)
   → Node 4 builds: generation script, asset storage, delivery

→ Coaching / service booking
   → Use: Cal.com embed or Calendly
   → Node 4 builds: booking link delivery on payment, Resend email

→ Pure landing page / lead gen (no fulfillment)
   → Use: Resend + Convex
   → Node 4 builds: email capture, confirmation sequence

→ Retainer / agency service
   → Use: Resend + optional Notion/Slack webhook
   → Node 4 builds: onboarding trigger on payment
```
